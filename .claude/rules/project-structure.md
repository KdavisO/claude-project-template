### ディレクトリ構造
```
src/
  app/              # Next.js App Router
    api/            # APIルート（RESTエンドポイント）
    (auth)/         # 認証関連ページ（Route Groups）
  components/       # UIコンポーネント
```

### 命名規則
- コンポーネント: PascalCase（`UserProfile.tsx`）
- ユーティリティ: camelCase（`formatDate.ts`）
- 型定義ファイル: camelCase（`user.ts`）
- テスト: `*.test.ts` / `*.test.tsx`（テスト対象と同階層に配置）
- 定数: SCREAMING_SNAKE_CASE（`MAX_RETRY_COUNT`）

### 新規ファイル作成時のルール
- 既存のディレクトリ構造に従う。新しいディレクトリを作る前に既存構造を確認する
- 1ファイル1エクスポートを原則とする（barrel export の `index.ts` は許容）
- テストファイルはテスト対象と同じディレクトリに配置する

## セキュリティ

<!-- プロジェクト固有のセキュリティルールを OWASP Top 10 ベースで記載する -->
<!-- 例:
### 入力バリデーション
- ユーザー入力は**サーバーサイドで必ずバリデーション**する（クライアントサイドのみは不可）
- Zod 等のスキーマバリデーションを使用し、型安全にバリデートする
- SQL はパラメータ化クエリのみ使用。文字列結合によるクエリ構築は禁止

### 認証・認可
- 認証チェックは middleware で一元化する
- APIルートでは必ずセッション検証を行う（`getServerSession()` 等）
- RLS（Row Level Security）を全テーブルに適用する

### 機密データ
- APIキー・シークレットは環境変数経由で注入する。コード中にハードコードしない
- `.env` ファイルは `.gitignore` に含める
- ログに機密情報（パスワード、トークン、個人情報）を出力しない

### 依存関係
- `npm audit` / `pnpm audit` で定期的に脆弱性をチェックする
- メジャーバージョンアップ時はCHANGELOGを確認し、破壊的変更を把握してから更新する
-->

## コード品質

<!-- 定量的な基準を含めて記載する -->
<!-- 例:
### 関数設計
- 1関数の行数: **最大50行**。超える場合は責務を分割する
- 引数の数: **最大4個**。超える場合はオブジェクト引数にまとめる
- ネストの深さ: **最大3段階**。早期リターンで深いネストを回避する
- 循環的複雑度: **最大10**。分岐が多い場合はストラテジーパターン等で分割する

### 型安全性
- `any` 型の使用禁止（ESLint `@typescript-eslint/no-explicit-any` で強制）
- 型アサーション（`as`）は最小限に。型ガード関数を優先する
- API レスポンスは Zod スキーマで実行時バリデーションし、型を導出する

### lint・フォーマット
- コミット前に `pnpm lint` を実行（CI でも検証）
- Prettier によるフォーマットを統一する
- `console.log` はデバッグ用途のみ。本番コードでは専用ロガーを使用する

### テスト
- カバレッジ目標: ビジネスロジック **80%以上**
- テスト命名: `describe('関数名/コンポーネント名')` → `it('〜すべき')` の形式
- モックは外部境界（API, DB）のみ。内部実装のモックは避ける
-->
